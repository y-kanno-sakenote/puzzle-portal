# 星おき QA レポート 2026-09-08

対象: `index.html`（40問埋め込み）／独立検証コード: `tools/qa_check.py`（自前バックトラック・自前妥当性チェック・自前簡易論理ソルバー）＋ Node vm での JS 実走テスト（本レポートに手順を残す。スクリプト自体は使い捨てのため未保存）。

## 1. 一意性の独立再検証（40/40） — PASS
実装者の `gen_puzzles.py` は使わず、行ごとに列を選ぶ素朴なバックトラック（`qa_check.py: count_solutions`）で limit=2 まで数えた。40問すべて解1個、かつ解いた★の位置が埋め込みの `solution` と完全一致。

```
=== 1. 独立ソルバーで一意性再検証 ===
PASS: 40/40 一意解、かつ独立ソルバーの解が solution と一致
```

## 2. 盤面妥当性（領域数=N・各領域連結・★1つずつ・行列1つずつ・非隣接） — PASS
自前BFS（4近傍）で連結性、自前ループで行/列/領域/隣接をチェック。40問とも違反なし。

## 3. 難度の実態（自前・簡易論理ソルバー：候補1つ確定／領域候補が1行1列に収まれば消す／確定★の周囲消去、のみ） — PASS（実装者の主張と整合）
| 段階 | 論理だけで解けた本数 | 申告nodes範囲（自前ソルバー実測） |
|---|---|---|
| 入門 | 10/10 | 0 |
| 初級 | 10/10 | 0 |
| 中級 | 0/10 | 2〜12 |
| 上級 | 0/10 | 22〜66 |

nodes=0 申告分は自前の独立実装でも全問論理だけで解け、nodes>0申告分は全問解けない。実装者の `propagate()` と本質的に同じ規則を独立実装してもズレなし＝申告値は信用できる。「上級は総当たり感が強い」は実測として正しい（中級も含め0/20が単純推論だけでは解けない＝最低1回の仮置きが要る設計）。

## 4. JS実走（Node vm、先頭 `<script>` を抜き出して `HoshiOki` を実行） — PASS
- `countSolutions(p,2)` 40問すべて1
- `isSolution(p, p.solution)` 40問すべて true
- `check()` 境界: 0個★→`[]`、隣接のみ→`['adjacent']`、領域のみ→`['region']`、行のみ→`['row']`、列のみ→`['col']`（n=5 puzzle0 で該当ペアを自動探索して確認）

## 5. localStorage 壊れ値（vm + 最小DOMスタブで画面 `<script>` を実走） — PASS
非JSON／空文字／配列JSON／`last:2.5`／`last`負数・範囲外／`grid`値が数値・短い文字列・未知の文字混入／`cleared`が配列／`o`がnullや文字列／`getItem`が例外／`setItem`が例外 の16パターン、すべて例外を投げずに起動完了（`loadSave`のtry/catchと個別のNumber.isInteger/文字種チェックが効いている）。

## 6. spec.md との齟齬 — FAIL（2件、いずれも実害は軽微・数値ドキュメントの陳腐化）
- **中級の「実物のnodes」表記ミス**: spec.md 表は「4〜12」と書くが、埋め込み40問の実測は **2〜12**（該当: index 25 相当、tier内1本目 nodes=2）。生成時と別seedで再生成したか、生成後に手直しした形跡。
- **領域最小マス数の破り**: spec.md／`gen_puzzles.py` の `MINSIZE[8]=3`（"n≥7で3、1マスの領域は使わない"の根拠）に反し、埋め込み40問中1本（中級・n=8・nodes=6、regions先頭行 `fbbbbbaa` の領域`a`）が **2マスの領域**を持つ。`refine()` は「minsize以下に“縮める”移動を止める」ガードのみで、`grow_regions()` 由来の初期時点で既にminsize未満の領域を救済しない構造的な抜け穴。パズルとしては一意解・連結・非隣接など全て正しく、プレイ上の実害はほぼ無いが、spec記載の不変条件とは食い違う。

## 直すべき順
1. `gen_puzzles.py` の `refine`/`grow_regions` に「minsize未満の領域が残っていたら不採用」ガードを追加（現状は縮小防止のみ）。中級 index 25相当の再生成。
2. spec.md 表の中級「実物のnodes」を実測（2〜12）に合わせて更新。
3. （足さない案）5・6以外の追加検証は不要——JSロジック・保存形式は実測で健全、これ以上の境界値探索は費用対効果が低い。
