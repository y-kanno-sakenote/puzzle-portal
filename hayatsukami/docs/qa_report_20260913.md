## 4. 先着判定 ★FAIL（コード読解＋再現テスト）
仕様（spec.md）:「先に触れた方が先着（pointerdownの時刻で判定）」。
実装（index.html 478-494行）は、指が **threshold（品の高さの半分）を越えた瞬間** に `pending` へ push し、`requestAnimationFrame` 1回分だけ待って `pending` 内の最小 `t0`（pointerdown時刻）を採用する方式。
→ **pushされるタイミング自体がフレームで分かれると、pointerdown時刻での比較が機能しない。**

再現（`run_race_condition_test`、フレームを分けて手動flush）:
- TOP: pointerdown t0=**0**（先着のはず）。ただし指を引き切るのが遅い。
- BOTTOM: pointerdown t0=**50**（後）。だが即座に閾値を超えて先に `pending` へpush。
- 1フレーム目で `resolve()` が走った時点で pending には BOTTOM しかおらず、**BOTTOM が先に得点**（top:0, bottom:**1**）。
- 遅れて届いたTOPの入力は、既に次の札へ進行した後の judge() に渡り、無効化されて消える（誤爆・黙殺）。

→ **「後から触ったが速く引いた方が勝つ」不具合を実測で確認**。1フレーム（~16ms）以上の指の動かし始めの差で、pointerdown時刻に基づく先着保証は成立しない。二人対戦の核であるフェアネスに関わる欠陥。

## 直すべき順（最大3つ）
1. **先着判定（§4・FAIL）**: `pending` を1フレームだけで確定させず、両者の `pointerdown` 時刻を起点に一定の猶予（例:指の移動が閾値に届くまでの最大許容時間）を設けてから比較するか、閾値到達ではなく pointerdown 時刻そのものだけで即時に確定させる設計に変更する。実機（二人プレイ）でも体感で再現しうるため優先度最高。
2. 上記1と関連し、「判定確定後に遅れて届いた入力を次の札に誤爆させず、黙って捨てる」保証をコードコメントとテストで明示する（現状は偶然 idx が一致しない限り黙殺されるだけで、一致すれば次の札の得点に化ける可能性が残る＝未検証）。
